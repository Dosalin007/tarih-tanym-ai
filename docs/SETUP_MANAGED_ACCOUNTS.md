# Запуск входа по выданным логинам

Эта ветка заменяет Google OAuth на аккаунты, которые создаёт администратор. Ученик не вводит email и не выбирает себе роль. Пароли обрабатывает Supabase Auth, а не таблица профилей. Публичная регистрация должна быть отключена на сервере.

## Настройка проекта

1. Создайте отдельный тестовый проект Supabase. Миграция предназначена для новой схемы: если `public.profiles` уже существует, сначала сравните структуру; не удаляйте существующие данные.
2. Примените `supabase/migrations/202610060001_managed_accounts.sql` через SQL Editor или Supabase CLI.
3. В Authentication отключите **Allow new users to sign up**, Google и остальные ненужные провайдеры. Оставьте email/password. Минимальная длина пароля — 12. `supabase/config.toml` задаёт локальные параметры; наличие файла в GitHub само по себе не меняет настройки размещённого проекта.
4. В `config.js` укажите Project URL и публичный `anon` key. Это публичные настройки, не секреты. Никогда не публикуйте `service_role` или Google client secret.
5. Разверните Edge Function: `supabase functions deploy accounts`. Функция сама проверяет JWT через `auth.getUser`, затем роль и блокировку по БД. Поэтому в config.toml для неё задан `verify_jwt=false`; это НЕ означает отсутствие проверки внутри функции.
6. Задайте секрет функции `ALLOWED_ORIGINS`: точный HTTPS origin сайта, без пути и завершающего слеша; для нескольких адресов используйте запятую. Стандартные `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY` доступны функции в размещённом Supabase. Service-role ключ используется исключительно сервером.
7. Настройте ограничения частоты попыток входа в Supabase Auth. Проверьте перебор паролей, сетевые ошибки, CORS, HTTPS и ограничения функции до допуска учеников.

## Первый администратор

Создайте пользователя вручную в Supabase Authentication → Users → Add user:

- Email: `admin@accounts.tarih.invalid`.
- Пароль: отдельный случайный временный пароль минимум 12 символов. Не записывайте его в GitHub.
- Auto Confirm User: включён.

Скопируйте UUID созданного пользователя и выполните SQL, заменив только UUID и имя:

```sql
insert into public.profiles (id, username, name, role, grade, must_change_password)
values ('UUID_ИЗ_AUTH_USERS', 'admin', 'Администратор', 'admin', null, true);
```

Войдите на сайт с логином `admin` и временным паролем; затем задайте новый пароль. Других администраторов создавайте только через доверенную процедуру в Dashboard/SQL: веб-консоль намеренно создаёт лишь учеников и учителей.

Адрес `@accounts.tarih.invalid` — внутренний идентификатор, а не почтовый ящик. Письма и email-reset для него не работают. Потерянный пароль ученика сбрасывает администратор; пароль администратора восстанавливает владелец проекта через Supabase Dashboard. Отключённая самостоятельная регистрация обязательна, иначе посторонние смогут занимать логины через Auth API.

## Работа учителя-администратора

1. Откройте «Пользователи», заполните имя, уникальный логин, роль и класс.
2. Нажмите «Создать аккаунт». Случайный временный пароль показывается один раз. Передайте данные ученику лично и нажмите «Скрыть данные».
3. При первом входе ученик вводит временный пароль и выбирает новый. Старый пароль нельзя посмотреть; можно выдать новый.
4. «Блокировать» изменяет профиль в общей БД. Серверные операции проверяют блокировку при каждом запросе; открытый интерфейс обновляет состояние каждые 30 секунд. Уже скачанный статический материал невозможно забрать обратно.

## Граница готовности

Авторизация и управление профилями реализованы в коде, но нуждаются в проверке на реальном тестовом Supabase. Классы, учебные комплекты, аналитика, AI и Canva остаются демонстрационными. Локальные комплекты/классы разделены по UUID пользователя, но localStorage не является защищённым хранилищем на общем компьютере. Не вводите туда чувствительные данные. Настоящее вступление в класс с разных устройств ещё не реализовано.

Для будущих таблиц включайте RLS и проверяйте `public.has_active_account()` плюс владельца/членство в классе. Одной политики «authenticated» недостаточно. Не переносите роли из старых localStorage-профилей в БД. При запуске удаляются старые demo-профили и `tt_users` с прежними открытыми паролями.

Сброс пароля и блокировка — разные действия. Для подозрения на компрометацию сначала блокируйте пользователя, затем отзывайте его сессии в Supabase и выдавайте новый пароль. Тест отзыва старых access/refresh tokens обязателен перед production: unit-тесты с подставным Auth не подтверждают поведение размещённого сервиса.

## Проверки

- `node --test tests/accounts.test.cjs` (Node 24): серверная проверка ролей и ошибочных запросов с подставным Supabase.
- `node --check auth.js`: синтаксис клиента.
- `node tests/auth-browser.cjs`: браузерные сценарии, если установлен Playwright и его Chromium. В среде подготовки PR Chromium отсутствовал, поэтому этот тест не был выполнен.
- На тестовом Supabase: два ученика + учитель + администратор; прямые REST-запросы к профилям; попытки изменить роль/blocked; повторный логин; смена/сброс пароля; блокировка действующей сессии; отключённый signup; невозможность создания admin через функцию; два браузера/устройства.

Не объединяйте PR как готовый production-релиз до выполнения последнего пункта и настройки проекта.
