## Критичные: блокируют production

### C1. Google-вход не настроен — функциональный блокер

Строки 169–174:

```js
const SUPABASE_URL='PASTE_SUPABASE_PROJECT_URL';
const SUPABASE_ANON_KEY='PASTE_SUPABASE_ANON_KEY';
const supabaseReady=!SUPABASE_URL.startsWith('PASTE_')&&!SUPABASE_ANON_KEY.startsWith('PASTE_');
const sb=supabaseReady?window.supabase.createClient(SUPABASE_URL,SUPABASE_ANON_KEY):null;
```

`startGoogleOAuth()` возвращает ошибку настройки при `!sb` (182–190), `restoreGoogleSession()` сразу завершается (241–245). Реальная Google-регистрация не работает. Это не утечка ключа: опубликованы шаблоны. Просто подставить ключ недостаточно для устранения остальных проблем.

### C2. Авторизация доверяет данным браузера — критичный архитектурный риск

Строки 250–251:

```js
const profile=loadLocalProfile(email);
if(profile)startSession(profile);
```

Строки 219–227 проверяют локальный `user.blocked` и копируют `user.role` в localStorage. `page()` берёт роль и класс оттуда же (283–285). В `adminChangeRole()` и `adminToggleBlock()` (453–470) нет проверки подтверждённой сервером роли вызывающего пользователя:

```js
p.role=role;p.grade=grade;
localStorage.setItem(profileKey(email),JSON.stringify(p));
```

Пользователь может изменить свой локальный профиль/вызвать глобальные функции и открыть админ-интерфейс. На onboarding любой выбирает teacher самостоятельно (203–212). Пока общей базы нет, это подтверждённый обход локального интерфейса, а не доказанный захват чужой серверной базы. Подключение реальных данных без серверной авторизации превратит эту архитектуру в серьёзную уязвимость.

Исправление: профиль по `auth.users.id`, роли только из БД, запрет клиентских обновлений привилегий, RLS и проверка JWT/роли/blocked для каждого административного действия.

### C3. Админ-консоль управляет только одним браузером

`getAllLocalProfiles()` (422–430) перебирает `localStorage`, а блокировка только перезаписывает JSON (466–470). Список пользователей с других устройств отсутствует. Блокировка не отзывается централизованно и не прекращает уже открытую сессию. Комментарий «внести role='admin' в profiles» (171) не соответствует реализации: запросов к этой таблице вообще нет.

В дереве проверенного репозитория только README, index.html, SVG и JSON маршрутов: миграций, API и RLS нет. Это не доказывает, что где-то отдельно нет Supabase-проекта, но его настройки из репозитория проверить нельзя.

### C4. Казахский язык ломает инициализацию

Строки 308 и 313 обращаются к отсутствующим словарям:

```js
const translated=lang==='kz'?(I18N[trimmed]||trimmed):trimmed;
el.placeholder=lang==='kz'?(PLACEHOLDERS[el.dataset.ruPlaceholder]||el.dataset.ruPlaceholder):el.dataset.ruPlaceholder;
```

В актуальном файле определения I18N и PLACEHOLDERS отсутствуют. Они добавлялись в `662a35d`, затем удалены в `b155537`. При нажатии ҚАЗ возникает ReferenceError; `setLang` успевает сохранить `kz`. При последующей загрузке строка 473 падает до вызова `restoreGoogleSession()` на 474. Это регрессия, а не просто неполный перевод.

## Важные: следующий обязательный этап

### I1. Небезопасный контекст вывода данных — потенциальный DOM XSS

`esc()` (322) экранирует только `&<>"`, но email вставляется внутри JS-строки атрибута `onclick` (451):

```js
onclick="adminChangeRole(\''+esc(u.email)+'\')"
```

HTML-экранирование не защищает JavaScript-строку; апостроф не экранируется. В той же строке `u.grade` вставляется в innerHTML без обработки. Сейчас подтверждён источник из изменяемого localStorage, поэтому удалённый stored XSS против другого пользователя не доказан. При переносе этих шаблонов на общие серверные профили риск станет межпользовательским. Использовать DOM/textContent/addEventListener и валидацию типов.

### I2. Данные разных аккаунтов и остатки старых паролей

`tt_packages` и `tt_classes` общие для origin (325–329), logout (254–259) не удаляет эти данные и локальные профили. На общем школьном компьютере остаются имена, email, профили и материалы. Предыдущий `662a35d` сохранял `pass` в `tt_users`; новая Google-версия перестала записывать пароли, но миграции очистки `tt_users` не содержит. Само хранение языковой настройки в localStorage нормально; хранение там прав доступа и открытых паролей — нет.

### I3. AI и Canva не подключены

`ROUTES` (162) — строки идентификаторов. `makePackage()` (323) строит шаблон HTML и без проверки выставляет «✓ связано». `sendEntQuery()` (385–392) добавляет заранее заданный ответ «Запрос принят…» без сетевого запроса. Кнопки Canva/помощника показывают alert (69, 75). `plugin-routing.json` декларативен и не загружается клиентом. Нужен настоящий серверный вызов с контролем доступа, ошибок, стоимости и источников; на demo следует явно маркировать имитацию.

### I4. Классы, оценки и прогресс не реализуют полный сценарий

`joinClass()` (329) только находит класс в браузере и рисует сообщение, но не сохраняет членство. Другой компьютер этот класс не видит. `ENT` (330) и показатели учителя/ученика — константы. `answerEnt()` вычисляет correct (417), но не сохраняет попытку, балл и слабые темы. До использования для оценивания нужны общие таблицы классов, участников, заданий и попыток с RLS.

### I5. Банк ЕНТ ограничен, соответствие спецификации не подтверждено

В `ENT_DEMO_TESTS` (343–365) девять вопросов для шести разделов. Для turkic и mongol используются одинаковые общие вопросы о способе подготовки (396–398), а не содержательные задания по этим периодам. Ссылок на спецификацию/источники в банке нет. Не выдавать этот объём за готовую подготовку ЕНТ. Ответы открыты в JS: это допустимо для самопроверки, но не для защищённого оценивания.

### I6. Жизненный цикл сессии и конфигурация

Нет `onAuthStateChange`, отдельной обработки истечения сессии/ошибок восстановления; `getSession()` не должен служить серверной проверкой полномочий. Подключение SDK через `@2` (17) не фиксирует точную версию. CSP/HTTP-заголовки размещённого сайта не проверены; их отсутствие по одному HTML утверждать нельзя. Перед production нужны реальные проверки блокировки, истечения и отзыва сессий, зависимости, CSP и ограничение попыток входа.

## Отдельная оценка безопасности

Подтверждены недоверенные роли/блокировки, отсутствие общей модели доступа в коде, опасный HTML/JS-контекст вывода, сохранение локальных данных после выхода. Не подтверждены компрометация Google, утечка настоящих ключей, открытая удалённая БД или реальная атака между устройствами.

Публичный anon/publishable key в браузере сам по себе не секрет. `service_role` обходится без RLS и должен оставаться на сервере. RLS, права таблиц и проверки владельца защищают данные независимо от скрытых кнопок. Документация: https://supabase.com/docs/guides/database/postgres/row-level-security и https://supabase.com/docs/guides/api/api-keys.

## Порядок перехода к production с учётом нового решения владельца

1. Убрать Google и самостоятельную регистрацию. Выдавать логины/временные пароли через администратора. Устранить падение перевода.
2. Настроить Supabase Auth, отключить public signup/Google, создать profiles и первого администратора доверенным способом. Проверять роли только на сервере; включить RLS.
3. Развернуть сервер выдачи/сброса паролей, обязательную первую смену, блокировку, обработку ошибок. Проверить ограничения попыток входа и отзыв старых сессий.
4. Проверить отрицательные сценарии прямыми API-запросами: ученик не читает чужой профиль, не меняет роль, не создаёт аккаунты; заблокированный пользователь не получает защищённые данные.
5. Перенести классы, членство, задания, попытки и материалы в БД с отдельными правами. Удалить фиктивную аналитику, подтвердить работу с двух устройств.
6. Подключить реальные AI/Canva и проверенный банк ЕНТ, источники и журнал действий администратора. Сохранять результаты, не доверяя оценке из браузера.
7. Провести staging-проверку на тестовых аккаунтах, настроить резервное копирование/восстановление и контроль ошибок; затем ограниченный запуск в одном классе.

В сопутствующей ветке подготовлен код этапов 1–3 и инструкция SETUP_MANAGED_ACCOUNTS.md. Он не развёрнут и не сертифицирован как готовый production: нет доступа к настроенному Supabase, реальных проверок RLS и браузерного прогона. Учебные demo-функции из пунктов I3–I5 остаются отдельной работой.
